### 1.2 Core Architectural Principles Discovered in Code

1. **Dual-Adapter Architecture (`src/api/`):** Consumes an identical 50-method `BcamsApi` interface. In dev and standalone evaluation mode, an in-memory mutable store (`mock-adapter.ts`) simulates latency, duplicate detection, and persistence. In production, `HttpApiAdapter` connects to REST endpoints with Bearer token authentication and request timeouts.
2. **Capability-Driven Identity Hierarchy (`src/types/domain.ts`, `src/lib/permissions.ts`):** Users and institutional personas derive from a base `Person` domain model. Specializations (`Staff`, `Lecturer`, `Student`) share physical identity records and biometric enrollment profiles. Capturer roles (`session_capture`) are operational capabilities attached to Student identities, rather than distinct top-level administrative accounts.
3. **Consolidated Institutional Administration (`/academic/academia`):** Departments, HOD appointments, institutional policies (attendance thresholds, session timeouts, biometric minimums, staff hours), geofence calibration, session capturer designations, and academic progression are consolidated into a unified single-pane-of-glass administrative workspace with 4 tabs.
4. **Resilient Offline Architecture with Tamper Detection (`src/services/`, `src/stores/sync-store.ts`):** Offline attendance captures and gate clock events are persisted to browser/Electron IndexedDB (`bcams_offline_store`) with in-memory fallback. System clock rollbacks are detected by cross-referencing server wall-clock time against high-resolution monotonic hardware time (`process.hrtime.bigint()` in Electron or `performance.now()` in browser).
5. **Universal Configurable Data Ingestion & Extraction (`src/components/common/bulk-import-dialog.tsx`, `src/domain/export-utils.ts`):** Every registry (Students, Staff, Lecturers, Courses) provides a 4-step bulk import workflow with template downloads, CSV parsing, row-level validation, duplicate detection, and transactional persistence, alongside configurable export modals.
6. **Strict Role-Based Operational Scoping:** 
   - Super Admins operate institution-wide across all departments, devices, and gate records.
   - HODs are locked to their appointed department; cross-department views and filters are removed.
   - Lecturers are scoped to assigned course units; "My Courses" is read-only and unburdened by administrative controls.
   - Student Session Capturers are immediately redirected from administrative routes to `/attendance/capture`.
   - Gate Terminal operates as an unauthenticated self-service kiosk at `/gate`.

### 2.2 Electron Process Architecture & Security Boundaries

The desktop application enforces strict isolation between Node.js system capabilities and the renderer window.

#### Security Configuration (`electron/main.js:18-37`)
- `contextIsolation: true` — The renderer runs in an isolated execution context.
- `nodeIntegration: false` — Direct `require()` and Node.js globals are forbidden in the renderer.
- `sandbox: true` — Chromium process sandboxing is enforced.
- `webSecurity: true` — Same-Origin Policy is maintained.
- `allowRunningInsecureContent: false` — Mixed HTTP/HTTPS content blocked.
- Single-instance lock: `app.requestSingleInstanceLock()` terminates secondary launches and focuses the primary window (`electron/main.js:11-14, 233-239`).
- Navigation protection: `webContents.setWindowOpenHandler` blocks arbitrary new windows and dispatches external HTTP/HTTPS links to OS shell default browsers (`electron/main.js:45-50`).
- Permissions request boundary: `setPermissionRequestHandler` explicitly allows only `'geolocation'` for campus geofencing and denies all other hardware permissions (`electron/main.js:247-252`).

#### Preload Bridge (`electron/preload.js:1-31`)
The preload script exposes the `window.bcamsDesktop` object via Electron `contextBridge`. The methods are strictly mapped to IPC invokes:
- **System & Clock:** `getVersion()`, `getPlatform()`, `getSystemTime()` (returns `{ wallClock, monotonicNs, uptimeSeconds }`).
- **Window Controls:** `minimize()`, `maximize()`, `close()`.
- **Scanner Hardware:** `getScannerStatus()`, `connectScanner(transport)`, `disconnectScanner()`, `setScannerTransport(transport)`, `startScannerCapture()`, `cancelScannerCapture()`.
- **Device Telemetry:** `getDeviceInfo()`.

#### IPC Handlers in Main Process (`electron/main.js:84-219`)
- `app:getSystemTime`: Evaluates `process.hrtime.bigint()` to supply high-resolution nanosecond hardware time for tamper-proof clock verification (`electron/main.js:96-102`).
- `scanner:startCapture`: Simulates optical sensor exposure and ISO 19794-2 template extraction with an 850ms latency delay and rotation across a mock pool of 6 student biometric records (`electron/main.js:73-82, 150-204`).
- `device:getInfo`: Queries Node.js `os` module for CPU model, core count, memory allocation, release version, and host architecture (`electron/main.js:207-219`).

### 3.2 Detailed Screen-by-Screen Inventory

#### 1. Split-Screen Login Page (`/login`)
- **Source File:** `src/pages/auth/login.tsx` (344 lines)
- **Intended User:** All authenticated personnel (Super Admin, HOD, Lecturer, Student Capturer).
- **Layout & Visual Composition:**
  - **Left Panel:** Slate-to-indigo gradient featuring an intentional laptop frame mockup containing an active dashboard preview snapshot placeholder with telemetry badges.
  - **Right Panel:** Official institutional sign-in card with Email/Staff ID and password fields, password visibility toggle, discreet shortcut button to the standalone Gate Terminal (`/gate`), and a development persona selector dropdown (`dev-test-access.tsx`). Biometric login button is intentionally omitted.
- **Data & Mutations:** Invokes `useAuthStore.getState().login(userId)`. Automatically inspects `user.captureCapability`: if `'session_capture'`, redirects immediately to `/attendance/capture`; otherwise redirects to `/`.
- **Known Limitations:** In mock mode, typing arbitrary credentials in the form always authenticates as the default Super Admin (`user-sa`). Switching personas is accomplished via the Development Personas dropdown.

#### 2. Standalone Gate Attendance Terminal (`/gate`)
- **Source File:** `src/pages/gate/index.tsx` (416 lines)
- **Intended User:** Physical campus security turnstile kiosk; used by university staff members walking through campus gates.
- **Authentication State:** Fully public / unauthenticated. Runs outside `AppShell` and `ProtectedRoute`.
- **Layout & Visual Composition:** Fullscreen operational kiosk with live clock, station identity header ("Station: Main Campus North Gate"), scanner hardware indicator, connection status badge, central fingerprint capture zone, real-time result banner (success/error, punctuality classification), and a local audit feed of the 10 most recent scans processed at the terminal today.
- **Available Actions:** "Scan Fingerprint to Clock" button (triggers `scannerService.simulateScan()`), manual synchronization trigger.
- **Business Logic:** Automatically evaluates current time against punctuality policy (default 9:00 AM + 60 min grace). If already clocked in today, switches event type to `clock_out`. Additional scans beyond 2 are recorded but flagged as extra scans.

#### 3. Administrative Operational Dashboard (`/`)
- **Source File:** `src/pages/dashboard/index.tsx` (474 lines)
- **Intended User:** Super Admin, HOD, and Lecturers. (Student Session Capturers are intercepted and redirected to `/attendance/capture` at line 76).
- **Layout & Visual Composition:**
  - Top header with workstation sync status (shown for capturers, hidden for admins).
  - Stat Cards Grid (dynamic based on role): Total Students, Total Staff, Assigned Courses (Lecturer), Active Sessions, Today's Attendance, Today's Clock-Ins (Super Admin only), Average Attendance Rate, Pending Sync Events.
  - Two-column bottom layout: Scoped Recent Sessions list (5 items) and Recent Gate Clock-Ins (Super Admin only) / Assigned Curriculum Summary (Lecturer).
- **Data Scoping:** HOD metrics and recent sessions are strictly scoped to `user.departmentId`. Lecturer metrics are scoped to courses where `lecturerId` matches `user.staffId` or `user.id`.

#### 4. Academia Hub (`/academic/academia`)
- **Source File:** `src/pages/academic/academia/index.tsx` (149 lines)
- **Intended User:** Super Administrator only (`RoleGuard roles={['super_admin']}`).
- **Layout & Sub-Components:** Master administrative console with 4 tabbed panels:
  1. **Departments & HODs (`departments-tab.tsx`, 474 lines):** Established department cards with statistics (students, lecturers, staff, courses), appointed HOD name and staff ID, action buttons to Edit Department, Assign/Replace HOD, and Remove HOD responsibility.
  2. **Attendance Policies & Geofence (`policies-tab.tsx`, 573 lines):** Institutional configuration cards for Attendance Threshold percentage (default 70%), Session Duration Timeout (default 120 min), Minimum Biometric Activation Fingers (default 4), Staff Expected Work Hours & Grace Period (9:00 AM - 5:00 PM, 60 min grace), and Physical Campus Geofence calibration (live coordinate acquisition via HTML5 Geolocation API, radius adjustment, calibration timestamp).
  3. **Session Capturers (`capturers-tab.tsx`, 416 lines):** Registry of students designated with `session_capture` capability. Provides student search, department filtering, capability assignment modal (with active status filtering), and one-click revocation modal.
  4. **Sessions & Progression (`sessions-progression-tab.tsx`, 622 lines):** Academic Session establishing modal (validates `YYYY/YYYY` format and consecutive years), active semester switcher, and Bulk Academic Progression workflow (two-step preview and batch execution advancing student cohorts to the next level/session).

#### 5. Courses & Curriculum Catalog (`/academic/courses`)

#### 6. Sessions Ledger (`/sessions`)

- **Intended User:** Super Admin, HOD, Lecturer. (Student Capturers redirected to `/attendance/capture`).

Clicking any row navigates to `/sessions/:sessionId`.

#### 7. Session Details & Attendance Ledger (`/sessions/:sessionId`)

  - Action bar: Lecturer Biometric Authorization trigger (for Draft sessions), Start Session trigger (for Authorized sessions).
  - Attendance Ledger table: Lists all student attendance capture events for this session, showing student name, matriculation number, timestamp, capture endpoint device ID, sync status, and Clock Integrity status (`verified`, `suspicious`, `unverified`).
  - Individual Session Export Dialog: Exports individual session attendance records with Clock Integrity filtering to CSV.

#### 8. Session Capture Workspace (`/attendance/capture`)
- **Source File:** `src/pages/attendance/capture.tsx` (876 lines)
- **Intended User:** Dedicated exclusively to Student Session Capturers.
- **Layout & Visual Composition:**

  - Geofence Status banner: Validates device coordinates against institutional policy (`inside` or `outside`).
  - Large Biometric Sensor Interface: Visual fingerprint icon with 4-phase animation (`ready`, `scanning`, `processing`, `result`).
  - Student Capturer Self-Attendance processing banner.
  - Real-time result feedback banner: Displays student name, matric number, quality score, minutiae count, or duplicate capture warning.

## 4. Role, Identity, Capability, and Authorization Model

### 4.1 Person Hierarchy & Multi-Responsibility Identity

The authorization model in BCAMS distinguishes between a physical human identity (`Person`) and institutional responsibilities (`UserRole`, `PersonSpecialization`).

```
                    ┌────────────────────────────────┐
                    │             Person             │
                    │   id, fullName, departmentId   │
                    │   biometricStatus, 0-10 fingers│
                    └───────────────┬────────────────┘
                                    │
         ┌──────────────────────────┼──────────────────────────┐
         ▼                          ▼                          ▼
┌──────────────────┐      ┌──────────────────┐       ┌──────────────────┐
│     Student      │      │      Staff       │       │     Lecturer     │
│  matricNumber    │      │     staffId      │       │     staffId      │
│  currentLevel    │      │   designation    │◄──────┤  staffPersonId   │
│  academicSession │      │    staffType     │       │ assignedCourses  │
│captureCapability │      │ isLecturer, isHOD│       └──────────────────┘
└──────────────────┘      └──────────────────┘
```

- **Staff-Lecturer Linkage:** Every Lecturer is fundamentally a Staff member (`src/types/domain.ts:126-133`). `Lecturer.staffId` matches `Staff.staffId`, and `Lecturer.staffPersonId` links directly to the `Staff` record. A staff member can teach courses without losing non-academic or administrative attributes.
- **HOD Appointment:** An HOD is an appointed administrative responsibility held by an existing academic staff member. Only Super Admin can appoint or revoke HOD responsibilities (`src/lib/permissions.ts:62-64`).

### 4.2 The Capability-Based Capturer Paradigm

In BCAMS, a "Session Capturer" is **not a distinct account role**. It is modeled as an operational capability assigned to an active Student (`src/types/domain.ts:17, 74`).
- **Assignment:** Conducted via the Academia console (`/academic/academia` -> Capturers Tab) by calling `api.assignSessionCapturer(studentId, true)`.
- **Identity Preservation:** The student retains their matriculation number, department, academic session, course enrollments, and attendance records.
- **Workflow Interception:** When a user with `captureCapability === 'session_capture'` logs in or attempts to visit administrative routes (Dashboard, Sessions, Reports), route guards automatically redirect them directly to `/attendance/capture` (`src/pages/auth/login.tsx:42`, `src/pages/dashboard/index.tsx:75`, `src/pages/sessions/index.tsx:48`).
- **Sidebar Scoping:** In `src/components/layout/sidebar.tsx`, all administrative links check `!isSessionCapturer(user)`. The capturer sees only the "Session Capture" workspace item.

### 4.3 Role Scoping Rules & Data Visibility Boundaries

The permissions engine (`src/lib/permissions.ts`) enforces strict data scopes:

1. **Super Admin (`super_admin`):**
   - Unrestricted institution-wide access across all departments, courses, staff, students, and sessions.
   - Exclusive access to Gate Attendance records (`/gate/records`), Academia configuration console (`/academic/academia`), and institutional policy modifications.
2. **Head of Department (`hod`):**
   - Scoped strictly to their appointed department (`user.departmentId`).
   - Can register, edit, and bulk import Students, Staff, and Lecturers within their department.
   - Can manage departmental course offerings and lecturer teaching assignments.
   - Cross-department export and department dropdown filters are completely disabled or hidden in HOD views.
   - Disallowed from accessing `/gate/records` or modifying institutional policies.
3. **Lecturer (`lecturer`):**
   - Scoped strictly to assigned course units (`s.lecturerId === lecturerId || s.substituteLecturerId === lecturerId`).
   - "My Courses" view is simplified, read-only, and displays only courses where the lecturer is primary or substitute.
   - Reports view displays only course offerings assigned to them.
   - Cannot create sessions directly; must physically scan fingerprint on the capturer's machine to authorize session start and closure.
4. **Student (`student`):**
   - General students have no administrative desktop access. If assigned `session_capture`, operational access is restricted to `/attendance/capture`.

### 4.4 Gate Terminal vs Administrative Gate Records

The system strictly divides physical turnstile operations from administrative reporting:
- **Operational Turnstile (`/gate`):** Public, self-service kiosk. Does not require login credentials. Accepts physical fingerprint scans and records clock-in/out events locally with high-resolution timestamps.
- **Administrative Ledger (`/gate/records`):** Super Admin only. Displays the complete institutional employee clock history, Clock Integrity verification flags, punctuality statistics, and date-range CSV export.

### 5.3 Lifecycle States & State Transition Rules

#### Session Lifecycle (`src/types/domain.ts:219`)
```
[draft] ──(Lecturer Fingerprint Scan)──► [authorized] ──(Capturer Starts Session)──► [active]
                                                                                       │
                 ┌─────────────────────────────────────────────────────────────────────┴───────┐
                 │                                                                             │
(Same-Lecturer Fingerprint Closure)                                             (Duration Exceeds Policy Timeout)
                 ▼                                                                             ▼
              [closed]                                                                     [expired]
```

- **Transition Rules:**
  1. A session in `draft` state cannot capture student attendance.
  2. Transition from `draft` to `authorized` requires a successful biometric scan from the assigned primary or substitute lecturer.
  3. Transition from `authorized` to `active` is triggered by the Student Capturer. Once `active`, the biometric scanner accepts student fingerprint touches.
  4. Transition from `active` to `closed` **requires a biometric fingerprint scan from the EXACT SAME lecturer** (`session.lecturerId`) who authorized the session start (`src/pages/attendance/capture.tsx:70-75`, `src/api/mock-adapter.ts:85`).
  5. If the session duration exceeds the policy timeout (default 120 minutes), the session automatically transitions to `expired`.
  6. The `draft` state is an internal staging state and is filtered out of all administrative ledgers (`src/pages/sessions/index.tsx:127`, `src/pages/dashboard/index.tsx:136`).

#### Biometric Enrollment Status (`src/types/domain.ts:41`)
- `not_enrolled`: 0 fingers enrolled.
- `partial`: 1 to 3 fingers enrolled. Cannot be used for official attendance.
- `activated`: 4 to 9 fingers enrolled. Reaches the institutional minimum threshold for biometric verification.
- `complete`: All 10 fingers successfully captured and stored.

## 8. Hardware, Biometrics, Location, and Offline Architecture

### 8.1 Scanner Abstraction & Native IPC Drivers

Hardware integration is decoupled through `ScannerService` (`src/services/scanner-service.ts`):

```
       ┌────────────────────────┐
       │   HybridScannerService │
       └───────────┬────────────┘
                   │
         ┌─────────┴─────────┐
         ▼                   ▼
┌──────────────────┐ ┌──────────────────┐
│  isElectron()    │ │ Web Dev Runtime  │
│  IPC to Main     │ │ Browser Mock     │
│  (850ms Delay)   │ │ Rotation Pool    │
└──────────────────┘ └──────────────────┘
```

- In Electron, calls invoke `window.bcamsDesktop.startScannerCapture()`, which routes to `electron/main.js:150`.
- The main process simulates optical sensor exposure with an 850ms latency delay and returns an ISO 19794-2 biometric payload from a roster of 6 student profiles.
- In standard web browsers, it falls back to an internal rotation array.
- **Physical Native SDK Status:** The codebase does not bundle compiled native C/C++ dynamic libraries (e.g., SecuGen FDx SDK `.dll` / `.dylib` / `.so`). Hardware interaction is emulated through Electron IPC.

### 8.2 Biometric Enrollment & Matching Lifecycle

- **Enrollment Target:** 10 fingers (`src/types/domain.ts:328`).
- **Minimum Activation:** 4 fingers (`ENROLLMENT_ACTIVATION_MIN = 4`).
- **Template Storage:** Biometric minutiae records are represented as metadata objects (`FingerEnrollment`) with position, quality score, and enrollment timestamps. Raw binary minutiae blobs are not persisted in local plaintext.

### 8.3 Geolocation & Haversine Policy Enforcement

Geolocation verification is managed by `src/services/geolocation-service.ts`:
- Acquires current device latitude and longitude via HTML5 `navigator.geolocation.getCurrentPosition` with `enableHighAccuracy: true` and a 10-second timeout.
- Evaluates spherical distance in metres using the Haversine formula:
  $$d = 2R \arcsin\left(\sqrt{\sin^2\left(\frac{\Delta \phi}{2}\right) + \cos(\phi_1)\cos(\phi_2)\sin^2\left(\frac{\Delta \lambda}{2}\right)}\right)$$
  where $R = 6,371,000\text{ m}$.
- Compares calculated distance against the effective institutional policy radius (`geofence_radius`, default 200m). Returns `'inside'` or `'outside'`.

### 8.4 Time Integrity & Monotonic Clock Protection (FR-4)

To prevent clock-tampering attacks (e.g., workstation operators rolling system clocks back to falsify attendance):
1. **Calibration Anchor:** On successful sync, the server returns its authoritative UTC wall-clock time. The client pairs this with its high-resolution monotonic hardware time (`process.hrtime.bigint()` in Electron or `performance.now()` in browser) to form a `CalibrationPair` (`src/stores/sync-store.ts:22-26`).
2. **Event Verification:** When an event is captured offline:
   $$\text{ExpectedTime} = \text{ServerWallClock} + (\text{CurrentMonotonic} - \text{AnchorMonotonic})$$
   $$\text{Drift} = |\text{ActualEventTime} - \text{ExpectedTime}|$$
3. **Threshold:** If drift exceeds 5 minutes, the event is marked `clockIntegrity: 'suspicious'` (`src/stores/sync-store.ts:198-202`). If the device reboots while offline (monotonic anchor lost), events are marked `clockIntegrity: 'unverified'`.

### 8.5 Offline Event Queue & IndexedDB Persistence (FR-3)

- **Database:** IndexedDB database named `bcams_offline_store` (Version 1).
- **Object Stores:**
  - `pending_events` (KeyPath: `id`, Indexes: `by_timestamp`, `by_type`, `by_clockIntegrity`).
  - `calibration_meta` (KeyPath: `key`).
- **In-Memory Fallback:** If IndexedDB is blocked or running in an unsupported environment, an in-memory `Map<string, PendingQueueItem>` maintains queue state without crashing (`src/services/offline-queue-service.ts:18, 73-76`).

### 8.6 Real-Time WebSocket Infrastructure

- Handled by `src/services/websocket-service.ts`.
- Manages connection lifecycle to `ws://localhost:8000/ws/events`.
- Supports bidirectional pub/sub event dispatching for `'clock_event'`, `'attendance_capture'`, `'session_state'`, and `'device_alert'`.
- Includes an internal fallback generator (`startSimulation()`) that broadcasts background turnstile clock events every 25 seconds for demonstration purposes.
